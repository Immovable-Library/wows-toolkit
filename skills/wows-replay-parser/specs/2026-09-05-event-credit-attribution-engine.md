# 事件级归因引擎 设计文档

- 日期：2026-09-05
- 状态：设计蓝本（Tier 2/3，待实现）
- 归属：wows-replay-parser skill（分析层），数据源对接 wows-replays / wowsunpack
- 目标：从 rep 事件流重建"为什么"，产出专业走位/瞄准建议，且只报有证据支持的结论。

## 1. 问题与动机

仅读最终伤害/击杀/经验下结论会出错：同一个"伤害偏低"的表层症状，根因可以完全不同。

- 东京快车（佐治亚）：你在前面点亮，但两个克利夫兰 + 美因茨与你在同一隐蔽圈里并存，
  按点亮规则被互相清零，队友收割 —— 根因是团队交互 + 人群并存。
- 竞技神（佐治亚）：伤害偏低是因为炮塔散布 RNG 演你 —— 根因是随机散布，不是走位或瞄准。

若分析只输出"伤害低 = 没打好"，这两种都会被误判，用户只能一遍遍纠正。因此目标不是
"再给一个结论"，而是**枚举候选根因、逐项测量证据、只报有证据支持的项**，并明确标注
"当前数据测不了的项"。根因判定必须可复现、可核对。

## 2. 机制不变式（全链路必须遵守）

- **点亮归属**：点亮伤害只归属**唯一点亮该目标**的己方玩家。同一目标隐蔽圈内同时有 ≥2 个己方
  （同时侦测）时，该目标点亮伤害归零，双方都拿不到。
- **伤害归属**：伤害/击杀只认**命中者**。点亮者拿的是净 `scouting_damage`，不拿命中者伤害。
- **期望命中率必须来自游戏散布模型**（Sigma、最大散布、弹道），不得拍脑袋说"你打偏了"。

由此，`scouting_damage` 只能当"净结算证据"，不能反推逐目标因果，也不能把"低净点亮"解释成"没点亮"。

## 3. 数据源（wows-replays 已解码的输入）

| 数据 | 出处 | 用途 |
|---|---|---|
| `ArtillerySalvo` / `WeaponFired` | SHOT / shootOnClient | 射了几轮、装填循环、是否卡炮 |
| `TerminalBallisticsInfo` | 命中瞬间 | 落点坐标、速度、与装甲法线夹角、引信状态 |
| `ShellHitType` | SHOTKILL | 碰撞 + 命中类型（跳弹/过穿/装甲命中等） |
| `TorpedoData` / `TorpedoManeuverDump` / `TorpedoAcousticDump` | TORPEDO | 鱼雷投放角度、命中率、机动 |
| `Position`（0x0a）、出生点（0x23） | 包流 | 走位路径、与敌距离变化、是否被交叉火力 |
| `visibilityFlags` / `DetectedByHydrophone` | Vehicle 属性 | 目标是否被侦测、侦测原因 |
| `damage stat packets` | 伤害类别 | 分敌方/友方/点亮/潜在 + 受害者 -> 目标选择 |

**关键缺口**：上述没有"哪个玩家被记为某目标唯一侦察者"的**归属字段**（`visibilityFlags` 只给
目标侧状态 + 原因 flags）。所以逐目标点亮因果（H1）需要**新增侦测事件解析**；其余根因（瞄准、散布、
走位、目标选择）用已有数据基本可测。

## 4. 假设-证据目录

| 假设 | 证据来源 | 判定阈值（示例） | Tier 1 可测 | 事件级可测 |
|---|---|---|---|---|
| H1 队友收菜 / 人群并存 | 净 `scouting_damage`、队友伤害/点亮占比、目标死亡时序 + 侦测窗口 | 净点亮高于均值，但存在低亮高伤队友；若目标在与你并存点时被吃，则需侦测事件 | 部分（净额） | 是 |
| H2 散布 / 运气 | 已射轮数、实际命中率 vs 期望命中率、落点离散步进 | 命中率低于期望且落点/命中类型正常 -> 散布 RNG | 否 | 是 |
| H3 瞄准 / 落点错误 | 命中类型、与装甲夹角、HE 是否打上层建筑 | 高比例跳弹 / 过穿 / 常打上层建筑 -> 瞄准问题 | 否 | 是 |
| H4 走位 / 暴露 | Position 时间线、暴露舰数、是否被交叉火力、有无掩体 | 处于无掩体位且被 ≥3 艘有视线集火 -> 走位问题 | 否 | 是 |
| H5 目标选择 | 伤害分布、是否浪费高口径打满血目标 | 该收残血却持续输出满血 BB -> 目标选择问题 | 否 | 是 |
| H6 版本 / 装填 / build | 射速、炮管数、卡炮窗口、与你舰船特色匹配 | 装填循环被卡 / 口径与目标不适配 -> 结构问题 | 否 | 是 |

## 5. 命中率期望模型

用于区分 H2（散布/运气）与 H3（瞄准错误）。

- 输入：火炮弹道与散布（wowsunpack `ballistics` / game params：Sigma、最大散布、弹速、口径）、
  目标舰种/航向/距离、发射总轮数与命中统计。
- 输出：**期望命中数 / 期望命中率**。
- 判定：实际命中率明显低于期望 且 落点角度/命中类型正常 -> H2 散布 RNG；若命中类型多为跳弹/过穿
  或常打上层建筑 -> H3 瞄准错误。二者要能分开，不能只凭命中率一句带过。

## 6. 事件流 schema（跨语言边界）

Rust `wows-replays` 将解码结果规范化为事件流（jsonl / sqlite），供 Python 引擎消费。草案：

```text
salvos          {ts, ship_id, salvo_id, barrel, shells: [...]}
impacts         {ts, ship_id, victim_id, angle, hit_type, shell_hit, pos}
shots_available {ts, ship_id, n_turrets_ready, cooldown}
positions       {ts, ship_id, x, y, heading, speed}
detections      {ts, target_id, detected_by(?), reasons[:]}   # H1 需补 spotter id
damage_events   {ts, source_id, victim_id, category, amount}
```

实现上优先复用 wows-replays 已有的解码（salvos / terminal ballistics / damage stat / positions），
只做**规范化导出**，不重新实现包解析；H1 的 `detections` 需要新增解析。

## 7. 多假设引擎（Python，落在 wows-replay-parser）

1. 输入：事件流 + 目标玩家 + 限定的对局。
2. 对每个假设：算出证据值（测量 + 阈值），并与期望模型比对。
3. 归一化各假设的证据强度，只保留越过阈值的假设，输出 **根因 + 证据链**。
4. 输出示例（瞄准）："你 15km 打 32 度目标 AP，命中率 X% 低于期望 Y%，且多为跳弹 -> 建议等目标露侧或换 HE。"
5. 输出示例（走位）："2:00 你位于北侧无掩体位，被 3 艘有视线集火 -> 建议拉烟或退回山后。"

## 8. 不自欺规则（防止每次被用户纠正）

- 只报**能量到证据**的结论；测不了的项标注"需事件级数据"，绝不臆断。
- 命中率的"期望"必须来自游戏散布模型，不能拍脑袋。
- 结论用**证据链**（测量值 + 阈值），区分"净额证据"与"因果证据"；不做单一因果断言。
- 判定分级：`已证实` / `净额支持` / `疑似（需事件级）` / `无证据`，不混用。

## 9. 里程碑与范围

- M1：Rust 事件导出（salvos / terminal ballistics / positions / damage）规范化 -> 事件流落库。
- M2：命中率期望模型（wowsunpack 散布 + Sigma + 弹道）。
- M3：多假设引擎覆盖 H2 / H3 / H4 / H5 / H6（瞄准、散布、走位、目标选择）。
- M4：**侦测事件解析**（补 spotter identity）-> H1 逐目标多点亮归因。

M1-M3 用现有解码基本可行；M4 是唯一需要新增包解析的硬骨头，也是"逐目标谁开灯"的唯一途径。

## 10. 验证计划

- 用已知案例回归：东京快车（佐治亚，应判"人群并存 / 需事件级"）、竞技神（佐治亚，应判"散布 RNG"），
  并补瞄准、走位案例各一。
- 每局输出与人工判断核对，标注置信度；避免过度解释。

## 11. 边界与风险

- 散布/Sigma/弹道数据可得性依赖 wowsunpack game params 覆盖。
- 侦测事件（H1）的包格式未知，需先摸底；不可行时不臆测，标"需数据"。
- 版本差异（老版本无 0x22 或无战报结算）沿用现有 `fields_resolved=false` 降级，不做虚假归因。
